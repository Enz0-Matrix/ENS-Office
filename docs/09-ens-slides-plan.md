# ENS-Slides: план, этап 0

Статус: черновик для обсуждения (17.11.2026). Кода нет. После ответов на вопросы (раздел 9) решения
переносятся в `docs/02-decisions.md` как ADR-010 (модель и формат) и ADR-011 (общий код).

Обозначения: **★** рекомендуемый вариант, `путь:строка` ссылки на существующий код.

---

## 0. Исходные условия

- Стек тот же, что у ENS-Text (ADR-001, ADR-009): TypeScript + Vite, оболочка Tauri 2, на РЕД ОС 7 помощник
  с окном системного Chromium 128. Значит, ничего новее Chromium 128 без запасного варианта.
- Данные пользователя превыше всего (ADR-005): исходный файл меняется только по «Сохранить», неподдерживаемое
  не пропадает молча.
- ENS-Text уже доказал схему «ProseMirror + свой OOXML на TypeScript + `fflate`» (`app/text/src/docx.ts`, 1476 строк).
  PPTX тоже OOXML и тоже DrawingML, поэтому большая часть подходов переносится почти напрямую.

## 1. Модель данных слайда

Что должно быть в модели: презентация → слайды → объекты (фигура, надпись, рисунок, таблица, диаграмма, группа),
у каждого объекта положение, размер, поворот, порядок по оси Z, ссылка на заполнитель (placeholder) макета.
Единицы: EMU, как в PPTX (914 400 на дюйм; 16:9 = 12 192 000 × 6 858 000 EMU = 1280 × 720 px при 96 dpi).

### Варианты

**A. Своя модель «дерево объектов» (JSON) + ProseMirror только внутри надписей ★**
```
Presentation { size, theme, masters[], layouts[], slides[], meta: { lossy, raw } }
Slide        { id, layoutId, bg, objects[], notes: PMDoc, transition?, raw }
Obj          { id, kind, x, y, w, h, rot, flip, z, ph?, fill, line, text?: PMDoc, raw }
```
- Плюсы: слайд по сути «холст с объектами», а не поток текста; простая отмена (снимки/патчи JSON),
  простые хэши для версий; каждая надпись — отдельный документ ProseMirror со всей типографикой ENS-Text.
- Минусы: своя история отмены на уровне слайда (ProseMirror даёт её только внутри надписи); надо склеивать
  две истории (решается так: правка текста закрывается одной записью в общей истории при выходе из надписи).

**B. Всё в одном документе ProseMirror** (слайд = узел, объект = узел с атрибутами положения)
- Плюсы: одна история отмены, один буфер обмена, готовые транзакции.
- Минусы: ProseMirror заточен под поток; абсолютное позиционирование, группы и порядок Z ложатся на него плохо,
  NodeView на каждый объект (опыт `app/text/src/frameview.ts` показывает, что даже одна плавающая рамка
  требует ухищрений против перерисовки). На 100+ слайдах один огромный документ медленнее.

**C. Расширить модель фигур IronCalc** (`core/ironcalc/base/src/types.rs:339` `ens_shapes`, `app/table/src/engine.ts:29`)
- Плюсы: фигуры с отменой уже есть в Rust.
- Минусы: модель привязана к ячейкам (`row`, `column`, `dx`, `dy`), текст в фигуре плоский; тащить wasm
  движка таблиц в презентации ради фигур неоправданно. Не берём.

### Отрисовка
- **DOM + SVG, слайд фиксированного размера 1280×720 с `transform: scale()`** ★: текст — настоящий DOM
  (выделение, IME, проверка орфографии из ENS-Text работают), фигуры — SVG (контуры, стрелки, градиенты).
  Миниатюры слева — тот же DOM в уменьшенном виде (или кэш-картинка для больших презентаций).
- Canvas (как сетка `app/table/src/grid.ts`) быстрее, но редактирование текста на canvas — месяцы работы. Только
  для миниатюр, если DOM окажется медленным на 200+ слайдах (замер на этапе 1).

### Правило «один активный редактор»
Только надпись, в которой стоит курсор, получает живой `EditorView`; остальные отрисованы статическим DOM
из того же `schema` (через `DOMSerializer`). Так 300 надписей не держат 300 редакторов.

## 2. Формат PPTX

### Стратегия сохранения (главное решение формата)

**A. Генерировать файл заново из модели** (как ENS-Text: `exportDocx`, `app/text/src/docx.ts:1372`)
- Плюсы: проще, предсказуемо, чистый XML.
- Минусы: всё неизвестное теряется → почти любой реальный PPTX окажется «с потерями» и его нельзя будет
  сохранить поверх (правило ADR-005/ADR-009). Для презентаций это будет постоянно: анимации, SmartArt, видео.

**B. «Хирургия по исходнику»: храним исходные XML-части, при сохранении меняем только тронутое ★**
- У каждого объекта и слайда есть `raw` (исходный `p:sp`/`p:pic`/… как строка или DOM). Нетронутый объект
  пишется байт в байт, тронутый — пересобирается, но неизвестные дочерние элементы (`a:extLst`, `p:custDataLst`,
  анимации `p:timing` слайда) переносятся из `raw`. Неизвестные части архива (`ppt/media`, `embeddings`, `tags`,
  `customXml`) копируются как есть.
- Плюсы: потерь почти нет, сохранение поверх файла разрешено гораздо чаще; круг «открыть, сохранить, открыть»
  проверяется побайтовым сравнением нетронутых частей.
- Минусы: сложнее; при удалении объекта надо чистить ссылки в `p:timing` (анимация на удалённую фигуру ломает файл
  в PowerPoint) — это отдельная проверка.

**C. Гибрид: B для открытых файлов, A для созданных с нуля** — фактически то же, что B: новый объект просто не имеет `raw`.

### Что поддерживаем в первой версии (чтение и запись)
| Часть | Поддержка |
|---|---|
| `presentation.xml`: размер слайда, порядок слайдов | полностью |
| Мастер, макеты, тема (`theme1.xml`: цвета, шрифты) | чтение и применение; правка — этап 3 |
| `p:sp` с `a:prstGeom` (прямоугольник, эллипс, скругл., линия, стрелки, ~20 частых) | полностью |
| Текст `a:txBody`: абзацы, `a:rPr` (шрифт, кегль, цвет, Ж/К/Ч/З), выравнивание, списки `a:buChar`/`a:buAutoNum`, отступы, межстрочный | полностью |
| Автоподбор `a:normAutofit` (fontScale) | чтение и показ; пересчёт — этап 2 |
| `p:pic`: картинка, обрезка `a:srcRect` | полностью |
| `a:tbl` в `p:graphicFrame` | ячейки, объединение, заливка, границы |
| Заметки докладчика `notesSlide` | текст |
| Фон слайда (цвет, картинка) | полностью |

### Что сохраняем без изменений (показываем как есть или заглушкой)
Анимации и переходы (`p:timing`, `p:transition`), SmartArt, диаграммы (до этапа 2), OLE, видео и звук, `p:custGeom`
(свободные формы показываем через SVG-путь, но не правим), комментарии, разделы (`p14:sectionLst`), макросы (`.pptm` не открываем на запись).

Предупреждение о потерях — тот же механизм, что `DocMeta.lossy` в ENS-Text (`app/text/src/docx.ts:32`, `lose()` в `:184`),
но при стратегии B список будет почти всегда пуст.

### Что переиспользуем из docx.ts
- Разбор XML и помощники `parseXml`, `kids`, `kid`, `attr`, `relAttr`, `readRels`, `normalizePath` (`app/text/src/docx.ts:64–209`) —
  сейчас не экспортируются. Нужен вынос в общий модуль `ooxml.ts` (отдельный PR, см. раздел 3).
- DrawingML общий с DOCX: обрезка `cropXml`/`a:srcRect` (`:1075`), EMU `emuOf` (`:1081`), надписи `parseTextBox` (`:354`),
  `bytesToDataUrl` (`:279`), `hexColor` (`:351`).
- Определение типа по содержимому (ZIP + `[Content_Types].xml`) — ADR-005, уже в оболочке.
- ODP (Impress) — не в MVP; см. вопрос 4.

### Оболочки (без копирования, как сделал ENS-Text)
- Tauri: `app/slides/src-tauri/src/lib.rs` подключает `app/table/src-tauri/src/lib.rs` через `#[path]`, как
  `app/text/src-tauri/src/lib.rs:5`.
- РЕД ОС 7: возможность `slides` в `app/table/redos7/Cargo.toml:15` рядом с `text`, `app/slides/redos7` — только пакет.

### Как подключать общий код: варианты
- **A. Прямые импорты `../../table/src/...` и `../../text/src/...`** (как сейчас делает ENS-Text, `app/text/vite.config.ts:3`).
  Быстро, но появляется связь «слайды → текст», и правка в ENS-Text может сломать слайды незаметно.
- **B. Сначала вынести общее в `app/shared`** (интерфейс из `table`, текстовое ядро и `ooxml.ts` из `text`) ★ — уже
  предусмотрено в ADR-009 («вынос в общий пакет — когда…»). Третий редактор и есть этот момент. Отдельный PR до кода слайдов,
  с прогоном тестов ENS-Text и ENS-Table, без изменения поведения.
- **C. Копировать нужное в `app/slides`** — нет: расхождение копий и двойные исправления.

### Что нельзя связывать
- `main.ts` любого редактора (глобальное состояние, `view`, обработчики окна) — никогда не импортируется другим.
- `docx.ts` целиком и `pagination.ts` — слайдам не нужны постраничность и формат Word; берём только `ooxml.ts`.
- Движок IronCalc (`engine.ts`, wasm) — не тянуть в слайды ради фигур и диаграмм; данные диаграммы
  хранить своей маленькой таблицей (раздел 6, этап 2).
- Настройки и снимки восстановления — раздельные ключи на редактор, чтобы сбой в одном не трогал другой.

## 4. Показ и экспорт в PDF

### Полноэкранный показ
- **Fullscreen API (`requestFullscreen`) ★** — есть в Chromium 128 и в Tauri; слайд = тот же DOM-рендер, `scale` под экран,
  чёрные поля. Клавиши как в PowerPoint: F5 / Shift+F5, стрелки, пробел, PgUp/PgDn, номер + Enter, B/W (чёрный/белый экран),
  Esc. Переходы: «Растворение» и «Сдвиг» на CSS-анимациях в MVP, остальные — без перехода (но сохраняются в файле).
- Запасной вариант, если полноэкранный режим недоступен в окне помощника РЕД ОС 7: развернуть окно Chromium
  (`--start-fullscreen` при запуске второго окна помощником).

### Режим докладчика
- **A. Два окна + `BroadcastChannel` ★**: окно показа и окно докладчика (текущий и следующий слайд, заметки, таймер)
  синхронизируются сообщениями. `BroadcastChannel` есть в Chromium с 54. В Tauri — второе `WebviewWindow`, на РЕД ОС 7 —
  второе окно Chromium от помощника (то же происхождение `127.0.0.1`).
- Выбор монитора: Window Management API (`getScreenDetails`, Chromium 100+) требует разрешения и в окне `--app` может быть
  недоступен → запасной вариант: окно открывается на текущем экране, пользователь перетаскивает его клавишей Win+Shift+стрелка
  (подсказка на экране). Нестандартная идея: кнопка «Поменять экраны местами» — окна просто обмениваются ролями по сообщению.
- **B. Одно окно, докладчик на том же экране** (как «Обзор докладчика» в репетиции) — проще, но не решает задачу проектора.

### Экспорт в PDF
- **A. Печать в PDF системным окном** (как ENS-Text и ENS-Table): `@page { size: 1280px 720px; margin: 0 }`,
  один слайд на страницу (подход `app/text/src/main.ts:328`). Варианты «слайды», «заметки», «выдачи 2/3/6 на листе».
  Плюсы: готово, векторный текст. Минусы: зависит от системного диалога (на РЕД ОС — «Печать в файл»).
- **B. Прямой экспорт PDF без диалога**: в Tauri 2 готового «печать в PDF» для всех платформ нет [проверить на этапе 4]; на РЕД ОС 7
  помощник может звать Chromium `--headless --print-to-pdf` по временному HTML ★ (кнопка «Экспорт в PDF» без диалогов,
  тот же движок рендера, что и экран). Нужна проверка, что системный Chromium 128 на РЕД ОС 7 это умеет (умеет с 59).
- **C. PDF своим кодом (pdf-lib, MIT)** — полный контроль, но шрифты и текст придётся раскладывать самим. Не сейчас.

## 5. Шаблоны, мастер-слайды, темы

- **Модель**: тема (12 цветов схемы + 2 шрифта: заголовки/текст) → мастер (фон, стили заголовка и текста, заполнители) →
  макеты (11 стандартных: «Титульный», «Заголовок и объект», «Два объекта», «Только заголовок», «Пустой» …) → слайд.
  Цвет объекта хранится как ссылка на схему (`a:schemeClr accent1`), поэтому смена темы перекрашивает всё — как в PowerPoint.
- **Наследование свойств**: слайд → макет → мастер → тема (`a:lvl1pPr` и т. д.). Вычислять «эффективный стиль» одной
  функцией с кэшем; в модели хранить только прямые значения (как прямое форматирование в ENS-Text, `app/text/src/schema.ts:13`).
- **Варианты правки мастера**: (A) только выбор готовых тем и макетов в MVP ★, (B) режим «Образец слайдов» с правкой
  — этап 3. Редактор образца — тот же редактор слайда, но в другом контексте, затраты невелики после MVP.
- **Встроенные темы**: 6–8 своих (не копии Office): «Строгая», «Ведомственная» (под ГОСТ-стиль документов, как шаблоны
  ENS-Text в `templates.ts`), «Контраст» (для проектора), «Тёмная» и т. д. Шрифты — только поставляемые (Carlito, Caladea,
  Liberation/Arimo/Tinos), чтобы презентация одинаково выглядела на РЕД ОС и Windows.
- **«Мои шаблоны»** — `.potx`/`.pptx` в IndexedDB, тот же механизм, что `app/text/src/templates.ts:120–153`.
- **Нестандартно**: «Встроить шрифты-аналоги» при сохранении (PPTX поддерживает `p:embeddedFontLst`) — презентация с флешки
  на чужом компьютере не «поплывёт». Лицензии Carlito/Caladea (OFL) это разрешают. Этап 3.

### Набор файлов `app/slides/tests/fixtures`
1. **Синтетические** (генерируются скриптом, как `app/text/tests/make_fixtures.py`, через python-pptx, MIT):

2. **Из других программ**: один и тот же сценарий, сохранённый в PowerPoint 2016/2021/365, LibreOffice Impress 7.x,
   Р7-Офис, МойОфис. Проверяет диалекты OOXML.
3. **Реальные «тяжёлые»** (обезличенные): 100+ слайдов, 50 МБ картинок, анимации, SmartArt, видео, `.pptx` из шаблонов
   госорганов. Именно их «открыть, сохранить, открыть» доказывает, что ничего не теряем (вопрос 1).

### Виды проверок (Playwright, как `app/text/tests/run.mjs`; на Chromium 128, если доступен)
- **Круг без правок**: открыть → сохранить → сравнить архивы: все нетронутые части побайтно равны, изменено только
  то, что положено (`docProps/app.xml`, наш `customXml`).
- **Круг с правкой**: изменить одну надпись → в файле изменился только этот слайд; анимации других слайдов на месте.
- **Открытие в чужих программах**: LibreOffice `soffice --headless --convert-to pdf` открывает наш файл без ошибок;
  сравнение растров страниц нашего PDF и PDF LibreOffice (порог расхождения, не точное равенство).
- **Рендер**: снимки слайдов эталонного набора, сравнение с сохранёнными эталонами (регрессии вёрстки).
- **Производительность**: открыть 300 слайдов < 2 с, переключение слайда < 50 мс, память < 500 МБ (по аналогии с `prototypes/grid-bench`).
- **Надёжность**: сбой посреди сохранения (убить процесс) → исходный файл цел, снимок восстановления открывается.
- **Показ**: F5, навигация, выход; синхронизация окна докладчика.
- Общие тесты ENS-Text и ENS-Table — после каждого PR, затрагивающего `app/shared`.

## 9. Вопросы, которые блокируют решения

1. **Реальные PPTX.** Можете дать 5–10 обезличенных презентаций из вашей работы (откуда они: PowerPoint, Р7, МойОфис, Impress)?
   Без них набор тестов будет синтетическим, а круг «открыть, сохранить, открыть» — неубедительным.
2. **Что важнее: править чужие PPTX или создавать свои?** Если правка чужих файлов (присланных из других ведомств) — главное,
   берём стратегию B «хирургия по исходнику» (раздел 2), она на ~1 неделю дороже. Если в основном свои — можно начать с A.
3. **Общий код: делаем сначала `app/shared` (этап 0.5) или пока импортируем напрямую из `app/table` и `app/text`?**
   Первое — неделя на перенос без новых функций, зато слайды не ломают ENS-Text.
4. **ODP (LibreOffice Impress)** нужен? Только открыть, или и сохранять? На РЕД ОС он встречается чаще, чем в Windows.
5. **Диаграммы** — в MVP или после? В список MVP они не входят, но в презентациях отчётов они в каждой второй.
6. **Режим докладчика на двух мониторах на РЕД ОС 7** — обязательная часть MVP? Есть ли машина с двумя мониторами/проектором
   для проверки?
7. **Анимации и переходы**: достаточно «сохраняем как есть и не показываем», или в показе нужны хотя бы появление по щелчку
   (самая частая анимация в учебных и отчётных презентациях)?
